Known issues

There is no in-game settings menu yet. Each game keeps its own keybinds.ini, display.ini and settings.ini; display and control settings for all games go in shared/display.ini and shared/keybinds.ini in the data folder, and a key in a game's own file wins. Alt+Enter toggles fullscreen, and each game remembers its window's place and size; pads are read through SDL3; Tools of Destruction has keyboard controls, and mouse look that is off unless [mouse] look = on is set in its keybinds.ini.

Known issues in Tools of Destruction:

  • The picture flickers inside one cave on Fastoon.
  • Level loads stall while graphics pipelines are built; the game's own graphics-stall notice can show during them.
  • The quit entries of the pause menu (off unless RC_PAUSE_QUIT=1) are drawn below the menu's box, and QUIT TO MAIN MENU loads the last save again.
  • The game has not been played through, so later levels are untested.

All known issues, with how and when each was measured: docs/KNOWN_ISSUES.md.

About

Bring your own game. This repository holds only the port: source code, patches to the recompiler, tools and documentation. It contains no game code, game data, assets, keys or firmware, and it never will. To build a game you need your own copy of it and the decrypted EBOOT.elf made from that copy (requirements).

How it works, briefly

  • PPU (main CPU code): lifted to C ahead of time by ps3recomp and compiled into the Windows program, so no CPU emulator runs for the main game code at play time.
  • SPU (Cell co-processor code): the game's SPU programs are found in your EBOOT.elf and lifted to C the same way by the build steps; the runtime runs them as compiled code. A program not lifted yet runs in an interpreter.
  • Graphics: the game's RSX command stream is translated to Direct3D 12 as it runs, by the ps3recomp runtime.
  • System software: the PS3 libraries the game calls are reimplemented on PC APIs by the same runtime.

The toolchain is a Nix flake (nix develop, nix develop .#win for the MinGW-w64 cross compiler); the recompiler is the third_party/ps3recomp submodule, with this port's changes in port/patches/. Steps: docs/BUILDING.md.

How AI was used

This port is developed by one maintainer with AI coding agents. The agents write code, tests and documentation under the maintainer's direction; the maintainer decides what is done, reviews the changes and merges them. Run results in the docs give their date and how they were measured; guesses are marked ASSUMPTION:. The PS3 emulator RPCS3 is used as a reference to read, never as code to copy.

[0.3.0] - 2026-11-13 (pre-release)

Since 0.2.1 the launcher builds games, Deadlocked HD builds and boots, every other game was run again with scripted input, the window and display settings are new, and the stall while a level's graphics pipelines are built is shorter. Each game's line gives its playability state in this release (the states are defined in RELEASE-CRITERIA.md); no game was played through by hand. Known issues of this release: docs/KNOWN_ISSUES.md. Patch numbers name this repository's own fixes on top of ps3recomp, the files in port/patches/; they are not ps3recomp's numbering. Frame rates are frames presented to the screen per second, in every game's line.

[All games]

  • Window placement: each game's window remembers its place and size, and the game keeps drawing and running while the window is dragged or resized. Checked in scripted runs of Tools of Destruction, 2026-11-10 (Windows program under Proton on Linux).
  • FSR 1 upscaling as a setting: upscale = fsr1 (with upscale_sharpness 0 to 2) in display.ini; off by default. Checked in a scripted run of Tools of Destruction, 2026-11-10.
  • Shared settings: display and control keys in shared/display.ini and shared/keybinds.ini apply to every game, and a key in a game's own file wins. Tested on the host only, not yet in a game run.
  • Fixed a lost fence in the runtime's graphics fence queue (patch 7042): the queue published a slot before its value had landed, so a game could wait for a fence that never arrived and the renderer timed out. This was why Ratchet & Clank 1 froze after its intro. It is a general fix and is not specific to that game.
  • Fixed false downloadable-content ownership: a game's check for a file that is not installed now answers "not installed", as the console does, instead of "licensed" (patch 7046). This removed the unlock of A Crack in Time's pre-order content (a scripted run, 2026-11-10). The check reads the file's type, so a folder, pipe or socket with the file's name also counts as not installed (host test). All 4 One and Full Frontal Assault make the same call and get the new answer; what it changes in those two games was not checked.
  • Shorter stalls while a level's graphics pipelines are built (patches 7050, 7051, 7052, 7054 and 7061): the renderer builds the pipeline a draw is waiting for first, starts building pipelines of draws it sees coming, sizes its build threads from the PC's processor count, and stores every pipeline it built in its cache file, so the next start can build them before they are needed. Measured on Tools of Destruction only, scripted, from a new game with an empty shader cache: the longest stall, at Metropolis's first frame, was about 26 to 32 s without these changes (single runs of earlier builds, 2026-11-10/11) and 12.6 and 15.8 s with them (two runs of a build of this release's code, 2026-11-12). With the cache of an earlier start it was 1.3 s (one run, 2026-11-11, before the changes). At exit the renderer now waits for builds still running before it frees the pipeline store (found in code review; the exit path was checked in one scripted run). Shorter stalls remain after the level starts.
  • Two voice-chat event functions that games call were missing and now answer as on the console (patch 7048; host test only, no game run with it).
  • Host tests in CI: every push and pull request runs the runtime's host tests against the patched recompiler tree (no game data and no GPU needed; a skipped test counts as a failure) and the release tools' tests.
  • Playability badges in the README: one per game, each a dated, measured run, with the six states defined in RELEASE-CRITERIA.md. The badges are written from the game catalogue, so they cannot drift from it.
  • AGENTS.md: rules for AI coding agents that work on this repository.
  • New guide: docs/ONLINE.md, on online play (it does not work yet in any game) and how the port will connect to re-psn.

Install

No game program is released: you build it yourself from your own copy of the game. The launcher preview is a download.

The launcher lists the games, finds your files, and builds a game from your own copy (Build, Rebuild, Cancel), then starts it (Play). Each game shows how far it gets in the current release. Download it from Releases (the newest launcher-v… release; each game also has notes-only releases such as tods-v…); Python is included, nothing else to install.

Downloads. Each launcher release has two: the bare launcher (Qwarks-Awakening-<version>-launcher-windows-x64.zip), which asks before it fetches the build files from GitHub on your first Build, and the full build zip, which carries the same files for a build with no download. A SHA256SUMS file lists the checksum of every zip.

  • Windows 10/11: unzip, start Qwarks-Awakening-launcher.exe. Caveat: not tried on Windows yet.
  • Linux: unzip, start Qwarks-Awakening-launcher.exe under Proton. Caveat: tested only by starting it with GE-Proton11-7 directly; through Steam and on the Steam Deck it is untested.

To build a game today, follow docs/BUILDING.md (Linux with Nix).

Where your data goes. There is no installer yet. The developer build reads your own game folder and keeps its saves and caches in folders you point it at. Each game writes its log, and a crash report if it crashes, to logs/<game>/ beside the program; your user name and home folder are removed from them, so a log can be attached to an issue as it is.

What goes online. The port has no crash upload and no telemetry; crash reports stay on your PC. The launcher connects to nothing on its own, only when you choose: with the small launcher download, the first Build offers the build kit (the port's source, the recompiler, a compiler, CMake and Ninja; the full build download already holds it), showing its size and its address on this repository's GitHub releases, and downloads it only when you choose Download, checked against a fingerprint built into the launcher and refused if anything differs. "Check for new releases" in Settings, off by default, asks GitHub's release list once at start which release is newest; the launcher never downloads a release or a game update by itself (game updates come from your own copy). The launcher's own debug information is downloaded only when you press its Download button in Settings. The cover-art switch, off by default and not wired yet in this version, will download cover images from IGDB.com once it works. Debug information for your games is off by default; when on, each build writes it to a file beside the game, never uploaded. The launcher's Online settings are off by default and only write a settings file on your PC, kept for when the games go online. The network and PlayStation Network functions the games call answer as a console with no connection does (tested on the host, not yet in a game run), unless the developer switch PS3_NET_ONLINE is set. Online play is not supported yet.
