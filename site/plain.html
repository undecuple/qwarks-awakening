Known issues

There is no in-game settings menu yet. Each game keeps its own keybinds.ini, display.ini and settings.ini. Display and control settings for all games go in shared/display.ini and shared/keybinds.ini in the data folder. A key in a game's own file wins. Alt+Enter toggles fullscreen, and each game remembers its window's place and size.

Controllers: pads are read through SDL3.

  • DualShock 4: played by hand (Tools of Destruction, 2026-10-22).
  • Keyboard: default keys for every pad button, played by hand (Tools of Destruction, 2026-11-03).
  • Mouse look: off unless [mouse] look = on is set in keybinds.ini; checked in scripted runs only.
  • Other pads SDL3 supports (Xbox, DualSense, Switch Pro and others): not tested.

Known issues in Tools of Destruction:

  • The picture flickers inside one cave on Fastoon.
  • Level loads stall while graphics pipelines are built; the game's own graphics-stall notice can show during them.
  • The quit entries of the pause menu (off unless RC_PAUSE_QUIT=1) are drawn below the menu's box, and QUIT TO MAIN MENU loads the last save again.
  • The game has not been played through, so later levels are untested.

All known issues, with how and when each was measured: docs/KNOWN_ISSUES.md.

About

Bring your own game. This repository holds only the port: source code, patches to the recompiler, tools and documentation. It contains no game code, game data, assets, keys or firmware, and it never will. To build a game you need your own copy of it and the decrypted EBOOT.elf made from that copy (What you need).

How it works, briefly

  • PPU (main CPU code): lifted to C ahead of time by ps3recomp and compiled into the Windows program. No CPU emulator runs for the main game code at play time.
  • SPU (Cell co-processor code): the build finds the game's SPU programs in your EBOOT.elf and lifts them to C the same way. A program not lifted yet runs in an interpreter.
  • Graphics: the ps3recomp runtime translates the game's RSX command stream to Direct3D 12 as it runs.
  • System software: the same runtime reimplements the PS3 libraries the game calls on PC APIs.

Native Windows source builds fetch the pinned llvm-mingw, CMake and Ninja archives and run through PowerShell and Python; Linux builds use the Nix flake (nix develop, nix develop .#win for the MinGW-w64 cross compiler). The recompiler is the third_party/ps3recomp submodule, with this port's changes in port/patches/. Steps: docs/BUILDING.md.

How AI was used

This port is developed by one maintainer with AI coding agents. The agents write code, tests and documentation under the maintainer's direction. The maintainer decides what is done, reviews the changes and merges them. Run results in the docs give their date and how they were measured; guesses are marked ASSUMPTION:. The PS3 emulator RPCS3 is used as a reference to read, never as code to copy.

[0.4.1] - 2026-11-23 (pre-release)

Summary: The builds that stopped with a missing file in 0.4.0 have their files again, and the games' code moves on: All 4 One runs on in its first level past the point where it froze and draws its busiest scenes faster, Into the Nexus reaches its first level and Ratchet stands in it, Full Frontal Assault reaches its first level and keeps drawing there, and two levels of Tools of Destruction that stopped drawing now run on.

A fix release on top of 0.4.0. The 0.4.0 downloads lacked files that the builds of A Crack in Time, All 4 One, Full Frontal Assault, Into the Nexus and Deadlocked HD need, so their Build stopped with a file-not-found error. This release carries them, and its game code is new since 0.3.1 (0.4.0 shipped 0.3.1's game code). Each game's line gives its playability state in this release (the states are defined in RELEASE-CRITERIA.md); no game was played through by hand. Known issues of this release: docs/KNOWN_ISSUES.md. Patch numbers name this repository's own fixes on top of ps3recomp, the files in port/patches/.

[All games]

  • The build files are complete again (issues #45 and #23): 0.4.0's downloads lacked the SPU tables tools/spu/<game>_raw_spu.json of A Crack in Time 1.20, All 4 One, Full Frontal Assault and Into the Nexus and every table Deadlocked HD reads, so Build stopped at the step that recompiles the game's SPU code. The list of build files is now taken from each released game's own build description instead of a hand-kept list, and the release is refused when one of them is missing. Checked with a test that compares the downloads' build files with what each game's build reads (against 0.4.0's file list it names exactly the missing files). A build from the new downloads on a player's machine has not been confirmed yet.
  • In an install folder whose name holds an apostrophe, such as the installer's default folder Qwark's Awakening, Build stopped at the link step with "no such file or directory" for pairs of object files (issue #44). The link step's file list was read with the wrong quoting rules, so the apostrophe was taken as the start of a quoted name. It is now read with the Windows rules it is written with. Checked with a host test and confirmed on a Windows 11 PC: Quest for Booty builds in the default folder.
  • On a Windows PC where Control Flow Guard is enforced for every program, the games closed at start-up with the error 0xc0000409 (issue #22; turning Control Flow Guard off for the game's program was the way round it). The games now use their own form of the jump they make while starting (patch 7066), which that check does not stop. Checked with a test under Wine and in scripted runs under Proton; not yet confirmed on a Windows PC with Control Flow Guard on.
  • A game that cannot open its window or start Direct3D 12, or that fails while it boots, now shows an error box that names its log file and ends with an error code. Before, it could keep running with no window. Not yet seen in a failing start.
  • Fixes found by comparing with another port of Tools of Destruction (credited in NOTICE.md), each with a test outside the game; none is checked for a visible change in a game yet: shaders that read the pixel position's w get 1/w as on the PS3 (patch 7108) and normalising a zero vector gives zero instead of an invalid value (patch 7112); a game's save list comes in the order the game asks for, such as newest first (patch 7109); the system cache is kept for the same game after a clean exit and emptied otherwise (patch 7110); a second wait on the same SPU event flag is refused as on the PS3 instead of sleeping for good (patch 7111).
  • With the pipeline look-ahead switched on (LD_PSO_AHEAD=1; off by default since 0.3.1), a draw whose graphics pipeline was not built yet waited for another pipeline, and the graphics device could be lost. It now waits for its own (patch 7082). Checked with a test outside the game; the look-ahead stays off by default.
  • The shader translator handles six more fragment-program instructions (STR, SFL, DST, LIT, DP2A, RFL; patch 7067), and inline vertex arrays larger than the old buffer are drawn whole (patch 7068). Checked with tests outside the game and scripted runs of Tools of Destruction.

[ToD] Tools of Destruction: in game

  • Zordoom Prison and Meridian City, the two levels that stopped drawing when started directly with the game's developer level option (a known issue of earlier releases), now run on. A collision job on the SPUs calls code that the port runs in its SPU interpreter instead of as recompiled code; on the way back the port did not stop at the return address, so each pass of the job's loop went one call deeper until the SPU halted (patch 7120). With the fix, both levels drew frames to the end of 300-second scripted runs with no input, and so did Kerchu City and a scripted new game in Metropolis (420 seconds), where the same kind of stop had shown in one earlier run each (2026-11-24). With the fix switched off, Zordoom Prison stopped again after 113 seconds. On the build with all of this release's patches, a scripted new game and the levels from Metropolis to Kerchu City, each started directly, reached their levels and drew to the end of their runs (2026-11-24). Loading and drawing only, not play.

[A4O] All 4 One: boots

  • Luminopolis runs on past the freeze about 468 seconds in. The game's sound job list on the SPUs checks the interrupt state and stops when interrupts are on; the port reported them on while the jobs ran, which the PS3 never does (patch 7105). A scripted new game now runs in Luminopolis to the end of a 600-second run (2026-11-19 and 2026-11-20), and scripted runs that load saves from later points reached their levels (creature_collector and Luminopolis, 2026-11-20). The scripted runs do not move the characters, so whether they still fall through the floor (see docs/KNOWN_ISSUES.md) is not checked yet.
  • The busiest scenes draw faster. The game keeps an occlusion query (a count of the pixels that pass the depth test, made by the GPU for the game) open over thousands of draws, and while one was open the port could not hand the frame's draws to the GPU in parts: the GPU got most of a frame in one piece and the game waited for it. The port now ends such a query where it hands a part over, begins it again in the next part and adds the parts' counts, so the game gets the same results as before (patch 2173; checked with a host test, not yet against the GPU's own counts in the game). In two scripted runs from the same Luminopolis save with the same input, one with the change switched off (2026-11-24), frames with 6,000 draws or more went from 6.6 to 8.6 frames per second over seconds 400 to 720, and frames with under 4,000 draws from 10.3 to 11.6; both runs had the port's frame profiler on. Both figures are still low.

[FFA] Full Frontal Assault: boots

  • The title screen (PRESS START) is drawn: the game asks for the current user's details at start-up, and the port now answers with the signed-in user (patch 7083), so the game's save-data check runs and the front end continues (scripted run, 2026-11-18). A scripted new game then reaches the level phoenix_ph1, where the picture almost stops about four minutes after start (4 of 4 scripted runs, 2026-11-19 and 2026-11-20).
  • The picture no longer almost stops in phoenix_ph1. Once a frame the game writes a jump into its graphics command buffer at the point the GPU is reading, moves the buffer's write position and soon puts the old command back. The port's command reader looks at the write position only every few milliseconds, so it could find the old command already back and read on into data that holds no commands. The game's stores to the write position now reach the port's graphics library, which keeps the word the reader is about to read until it has read it (patch 7116). In 4 of 4 scripted runs (two new games and two from a campaign save, 420 seconds each, 2026-11-24) the game stays in phoenix_ph1 and keeps drawing to the end of the run, at no less than 7 frames per second in any minute after the level opened. The change is in code every game uses; scripted runs of All 4 One, Into the Nexus and Tools of Destruction on the same build reached their levels as before.

[Nexus] Into the Nexus: boots

  • A scripted new game now gets past the lobby, which stayed black in 0.3.1, to its first level, prison_transport. There a job on the SPUs stopped after about six minutes, because one call form in its code was recompiled as a call that never returns (patch 7106); a scripted run then stayed in the level for its full 960 seconds (2026-11-19).
  • Ratchet stands in the prison transport instead of falling through its floor. The game's collision job reads data from another SPU's memory through the address window the PS3 gives each SPU thread; the port served that window from main memory, so every ground check missed (patch 7115). In a scripted run (2026-11-20) Ratchet stands and walks in the prison transport to the end of the 600-second run. The script does not leave the first room yet.

[Launcher]

  • The Windows downloads and the Linux tar.gz now carry recomplauncher.json beside the launcher, so RecompLauncher can install the port from this release page, ask for your own copy of a game (the PS3_GAME folder or a disc image) and start the launcher (on Linux the program or the AppImage). It also offers the display settings the games already read (window mode, window size, picture shape, FSR 1 upscaler, VSync), written to the same shared display.ini the launcher uses. It ships no game files.
  • The launcher recognises more regional and digital releases of Tools of Destruction, Quest for Booty, A Crack in Time, the Collection and Deadlocked HD, marked as not tested: it names them as known releases and offers no build for them.
  • Digital copies (PSN) of a game are found and named as such: the game's card says "Digital copy: not yet supported" and names the disc (with its update) to use for now; digital copies are added one game at a time, once each has been checked. A game update given as a PKG file is no longer offered as an update: the launcher asks for the installed update folder instead. A disc copy with its update and a digital copy of the same game can sit side by side. Checked with tests outside the launcher.
  • The build check gives a reason instead of starting a build that ends in a black screen: an incomplete update, a PKG file, a partial disc folder, a missing disc, a damaged ISO, or build files that could not be installed. Checked with tests outside the launcher.
  • Add game files: the paths picked in the drawer now reach the build check (before, the drawer did not pass them on), a path the check refuses keeps Build off, and a game that needs attention cannot be built until it is fixed. When the launcher's engine cannot start, a box says so. Checked with tests outside the launcher.
  • A native Windows source build: tools\build-windows.ps1 fetches the pinned llvm-mingw, CMake, Ninja and SDL3 archives (checked against their SHA-256), prepares the patched ps3recomp copy, lifts and builds a game and stages it, with PowerShell and Python only (no WSL, Bash or Nix); see docs/BUILDING.md. A contributor reports that this path builds and boots the game natively on Windows (their own hardware); the project has not run it on Windows itself. The patched ps3recomp copy is now made by tools/ps3recomp_patched.py on every platform (tools/ps3recomp-patched.sh calls it); on Linux its tree is byte-identical to the old script's.
  • The build check accepts an ISO that was decrypted in place and still starts with the disc's table of clear regions: when the game program inside it is readable, the image counts as decrypted. Before, such an image was refused as encrypted. Checked with synthetic images only.
  • The launcher, the README banner, the GitHub preview image and the installer's pictures and icons now follow the same new look as the project page (dark navy, purple, cyan, a little gold; bolted panels, a holo grid and a progress dial), all drawn for this project.
  • The controller test in Settings is now a test you start and stop. While it runs, the controller no longer moves through the launcher, so every button can be pressed safely. It ends with Stop test, Esc, holding B for two seconds, or leaving the page, and the controller works the launcher again once all its buttons are released.

Online play through re-psn

Planned, not started in any game: ONLINE.md. The games with online modes on the console are All 4 One, Full Frontal Assault and Deadlocked HD; the order is not set. Off by default, one online method at a time, and nothing connects unless you choose it.

Co-op for the single-player games (optional)

If it proves possible: an optional co-op mode in the style of All 4 One for the single-player games, where a second player takes a second character. It would be opt-in, a change to the game that is off by default, and is only a plan until the first prototype shows it can work.

No game program is released: the launcher builds it on your PC from your own copy of the game.

The launcher checks your EBOOT.elf against the programs it knows. For a game with an update it needs the program from that update; a disc or older update program it knows is refused by name ("Wrong version"). The regions listed for one game share one program: their decrypted EBOOT.elf files are identical. A Crack in Time's EU (BCES00511, BCES00726, BCES00748) and JP (BCJS30038) 1.20 updates and the EU disc of Tools of Destruction (BCES00052) are different programs from the US ones, so the launcher refuses them by name ("Not supported yet"). Digital (PSN) versions are untested, apart from Deadlocked HD, which is digital only; an EBOOT.elf the launcher does not know gets the warning "Unknown build, may still work". The port was tested with one copy of each game; the other regions listed share its program but were not run.

Steps

  1. Download Qwarks-Awakening-<version>-setup-windows-x64.exe from the Latest release. You now have one setup file.
  2. Run it. The program is not signed, so Windows may show "Windows protected your PC". Choose "More info", then "Run anyway". The setup's welcome page opens.
  3. Click Next, Next, Install. The default folder is %LOCALAPPDATA%\Programs\Qwark's Awakening; you can pick another one. No administrator rights are needed. The last page says "Setup is done".
  4. Click Finish with "Start Qwark's Awakening" ticked. The launcher opens. On its first start it looks for your games in RPCS3's usual folders, reading only, and writes library.json in the install folder.
  5. Pick a game and click Build. If a game is missing, add its folder under Settings, Locations. The build takes a while. When it ends, the launcher says "Finished: ... is built and ready to play." Click Play.

Portable (no install): each launcher release also has two zips. The full build zip holds the same files as the setup. The launcher zip holds only the launcher; it asks before it downloads the build kit on your first Build. Unpack the whole folder, then start Qwarks-Awakening-launcher.exe. SHA256SUMS on the release page lists the checksum of every file.

Linux: download qwarks-awakening-launcher-<version>-linux-x86_64.tar.gz from the same release, unpack it and run ./install.sh in its folder. It installs the launcher for your user (no administrator rights) with a menu entry; install.sh --uninstall removes it again. Or take qwarks-awakening-launcher-<version>-x86_64.AppImage, the same launcher in one file that runs where you keep it: chmod +x it and start it (on NixOS: appimage-run). docs/LINUX.md has the details and the Proton choice.

Uninstall from Windows Settings, Apps, or from the Start menu. The uninstaller removes the program files. It asks before it deletes your library, your built games with their saves, and the logs. Then it asks before it deletes the games' settings. Both answers default to No.

Where your data goes. The launcher keeps your library (library.json), built games, build files and logs in its install folder. Each game keeps its saves in gamedata\ beside its program unless you choose a saves folder in Settings, Locations. The games' settings are in %APPDATA%\Qwark's Awakening. Each game writes its log, and a crash report if it crashes, to logs/<game>/ beside its program. Your user name and home folder are removed from them.
